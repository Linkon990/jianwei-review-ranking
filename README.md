# 见微 · 商品评论排序

把评论的可见位置、停留时间和后续选择接起来，观察它们如何改变下一位访客看到的排序。范围只在商品详情的评论区。

[在线体验](https://jianwei-review-ranking.pages.dev/) · [算法原理](docs/algorithm.md) · [运行与部署](docs/deployment.md)

网页是一轮六位访客的交互演示：进入评论、滚动阅读、选择结果，再看评分怎样更新。商品和 72 条评论都是合成数据，结果由体验者选择，不发生真实交易。

## 算法怎样工作

```mermaid
flowchart LR
    A["测量<br/>可见位置 × 停留"] --> B["更新<br/>归一化份额 · 结果反馈"]
    B --> C["排序<br/>先验 · 约束 · 探索"]
```

每条评论连续可见至少 1 秒、可见比例不低于 50%，才进入计算。重叠时间只计一次，每条评论在一个片段中最多累计 30 秒。可见时长乘上位置权重后，归一化为本次结果的分配份额，避免把一笔购买重复算成多笔证据。

三种位置方案使用相同输入。表中是屏幕从上到下八个位置的显示权值，计算时除以 8。

| 方案 | 滑动后的权值 |
| --- | --- |
| 均匀 | 8, 8, 8, 8, 8, 8, 8, 8 |
| A · 下方递增 | 1, 2, 3, 4, 5, 6, 7, 8 |
| B · 中下区域 | 1, 3, 5, 7, 8, 8, 7, 5 |

首屏统一为 8。网页默认 B，便于观察位置变化；这不表示中下区域已经被证实更有效。

评分保留 70% 的质量先验，行为关联占 30%。排序还会让使用限制较明确的评论保留在前列，并以 10% 的概率从候选中随机选择首条，给其他评论留下被看见的机会。公式、算例和具体约束见[算法原理](docs/algorithm.md)。

## 体验方式

1. 选择位置方案，点击商品页的“查看全部评论”。每轮首次进入后固定方案。
2. 滚动评论，观察旁边的位置标尺和研究台。点开全文时，背后的列表暂停计时。
3. 选择“已支付”“未购买”或“购买后退款”。评分更新后交给下一位访客，六位完成后显示总结。
4. 手机内的“返回”保留本轮进度；研究台的“停止”清空整轮。完成后可开始新一轮。

公开网页在浏览器内计算。每个标签页独立，阅读记录和评分不上传，刷新或关闭后清空；仅深浅色偏好保存在本机。研究台的“可见时长（评论合计）”按评论分别累加，八条同时可见两秒会累计约十六秒，它不是页面停留时长。

## 运行

静态演示使用原生 HTML、CSS、JavaScript，无第三方运行依赖。在仓库目录执行：

```sh
python -m http.server 8080 --bind 127.0.0.1 --directory web
```

打开 [localhost:8080](http://127.0.0.1:8080/)。需要 Python 3.10 或更高版本。

构建 Pages 部署目录需要 Node.js 20 或更高版本，不需要安装 npm 包：

```sh
npm run build
```

构建结果位于 `site-dist/`。Cloudflare Pages 使用 `npm run build` 和输出目录 `site-dist`，配置见[部署说明](docs/deployment.md)。

仓库也保留 Python 参考实现及本地服务：

```sh
python -m src.demo_server
```

打开 [localhost:8765](http://127.0.0.1:8765/)。此模式由本机服务保存当前轮次，刷新不会清空服务中的状态；多标签页共用该进程。它只监听本机地址，用于阅读代码和本地对照。

## 还存在的不足

可见不等于认真阅读，停留也不一定表示认同。付款同时受价格、优惠、既有意愿等影响，这里的分配份额只表示关联，不能证明某条评论导致购买。

位置权重、阅读阈值、先验比例和探索率都需要真实数据校准。更多行为数据也可能强化原有曝光偏差；目前六位访客的演示不能验证转化提升，首位探索日志也不能用来评估任意整页重排。

未购买或退款可能来自准确的负面信息，不能简单把它理解为评论没有价值。当前限制信息约束只是一条基础规则，尚未解决内容真实性、完整主题覆盖、个性化需求或刷量问题。

尚未接入真实平台、订单与退款回流，也没有开展真实随机试验。Python 参考实现保留购买窗口与退款成熟规则；网页按钮压缩了等待过程，仅用于演示计算。
